# Git・ブランチ運用ルール

このドキュメントは、人間の開発者とCodexなどのAIコーディングエージェントに共通するGit運用の原則を定めます。

## 基本原則

- `main`、`develop`へ直接コミット・直接Pushしない。
- 作業を始める前に、原則として最新の`develop`から作業用ブランチを作成する。
- 1つのブランチには、原則として1つの機能、修正、または文書整備だけを含める。
- 別の目的の変更が必要になった場合は、同じブランチへ混ぜず、別Issue・別ブランチとして分ける。
- Push前に、変更内容、コミット履歴、混入ファイル、実行した確認コマンドを確認する。
- 作業用ブランチから`develop`へPull Requestを作成し、レビュー後にマージする。

## ブランチ命名

ブランチ名は次の形式を使用します。

```text
<type>/<issue-number>-<short-description>
```

Issueがない作業では、`<issue-number>-`を省略できます。ただし、実装作業は原則として先にIssueを作成してください。

| type | 用途 | 例 |
| --- | --- | --- |
| `feature` | 新機能 | `feature/31-quest-completion-api` |
| `fix` | 不具合修正 | `fix/42-duplicate-quest-order` |
| `docs` | ドキュメント | `docs/18-update-api-guide` |
| `refactor` | 挙動を変えない整理 | `refactor/27-quest-service` |
| `test` | テスト追加・修正 | `test/35-study-log-api` |
| `chore` | 設定・保守作業 | `chore/update-biome-config` |
| `ci` | CI変更 | `ci/add-api-check` |

短い説明には英小文字とハイフンを使用し、`update`や`work`だけの曖昧な名前は避けます。

## Codexで作業する場合

Codexも人間と同じブランチ運用に従います。

1. 作業開始時に現在のブランチと作業ツリーを確認する。
2. `main`または`develop`上にいる場合は、変更前に作業内容に合った新しいブランチを作成する。
3. すでに作業ブランチ上にいる場合でも、依頼内容とブランチの目的が異なる場合は新しいブランチへ分ける。
4. ユーザーや他メンバーの未コミット変更を、勝手に移動、削除、stage、commitしない。
5. 依頼された範囲だけを変更し、無関係な整形やリファクタリングを混ぜない。
6. Pushする場合は、作業ブランチだけをPushし、`main`や`develop`へ直接Pushしない。
7. 最終報告に、ブランチ名、コミット一覧、実行した確認、未実行の確認を記載する。

## コミットの分け方

コミットは、レビュー時に変更理由を1つのまとまりとして説明でき、必要ならそのコミットだけを取り消せる粒度にします。

分ける例:

- DBモデル変更とmigration
- API実装
- OpenAPI仕様更新
- フロントエンド画面実装
- テスト追加
- ドキュメント更新

同じ目的を達成するために密接に関連する小さな変更は、細かく分けすぎず1コミットにまとめて構いません。一方、次の変更は同じコミットへ混ぜません。

- 新機能と無関係なリファクタリング
- 不具合修正と別機能の追加
- 自動整形だけの大量変更と実装変更
- 複数Issueにまたがる変更

一時的な`WIP`、`修正`、`調整`だけのコミットは、Push前に適切な単位へ整理します。ただし、共有済みコミットの履歴を書き換える場合は、他メンバーへの影響を確認してください。

## コミットメッセージ

既存ルールを維持し、次の形式を使用します。

```text
prefix: 内容を日本語で記述
```

例:

- `feat: クエスト達成APIを追加`
- `fix: クエストの重複受注を防止`
- `docs: Git運用ルールを追加`
- `test: 学習記録APIの異常系テストを追加`

使用する主なprefixは、`feat`、`fix`、`docs`、`chore`、`refactor`、`test`、`style`、`ci`、`build`です。

コミットメッセージは、そのコミットで何が変わるかを具体的に表現します。`変更`、`対応`、`修正`だけの曖昧な内容は避けます。

## Push前チェック

```bash
git status --short
git branch --show-current
git diff --cached --stat
git log --oneline develop..HEAD
```

確認事項:

- 作業ブランチ上にいる
- ブランチ名が作業内容を表している
- コミットが作業内容ごとに分かれている
- 関係ないファイルや秘密情報が含まれていない
- 必要なテスト・lint・typecheck・buildを実行している
- 実行できなかった確認と理由を説明できる

## Pull Request

- 原則として1つのPRで1つのIssueを解決する。
- マージ先は通常`develop`とする。
- PR本文に変更概要、主な変更ファイル、確認方法、未実行の確認を記載する。
- 大きすぎるPRは、独立してレビュー可能な機能単位へ分割する。
- マージ後に作業ブランチを削除する。
